# 项目审计（2026-10-09）

审计范围：Mac 工作树、NAS 生产容器与磁盘、CouchDB 里程碑文档、`~/notes` 与插件状态。
性质：只读诊断，未修改任何代码、配置或容器。所有数字都是本次实测，不是从旧文档抄来的。

## 1. 结论先行

主链路是好的：知乎下载 → 写 `notes/` → NAS 节点 daemon 发布到 CouchDB → 管道探针核对后才消费收件箱。这条链在 2026-10-08 已端到端验证过，今天实测仍在跑（数据库游标从 101404 走到 107235）。

乱的不在代码，在三处：

1. **弯路残留**：NAS 上 5.3GB 的试验目录 + 2 个已退出的容器 + 7.5GB  backups，其中大部分是这两周试错留下的，没有一个还在被使用。
2. **文档漂移**：`README.md` 通篇还在讲"推送到 GitHub、Obsidian Git 拉取"，`config.example.yaml` 默认值还是 `git`，`AGENTS.md` 里三个日期的"当前状态"块互相矛盾。照着文档操作会走错路。
3. **两个没人看着的真实缺陷**：打标端点从 10-07 起每轮固定失败 18 条、每 2 小时刷一次 ERROR；无视频的想法（pin）被静默跳过，只打 DEBUG——而收藏箱现在正好只剩 2 条这种。

### 3.3 弯路本身的账（含我这次会话造成的）

诚实记录，避免下次重走：

1. 附件专用前缀 `assets/知乎附件/`：迁移 180 个目录 → 发现库里已有 399 篇笔记被移出 `知乎收藏/` → 全量回退。净收益 0，代价是 3400 文件级别的两次改名。
2. CLI 定点取件试了三种（`syncOnlyRegEx` 白名单、全新隔离库、`mirror`），全部撞上同一个天花板：**CLI 模式下复制结果不落库**，本地存储永远停在 6721 条。结论确定，不要再试第四种。
3. "Mac 丢了约 5900 个文件"是误判：库里 5860 个是陈旧重复文档（同一内容的旧路径）。按内容哈希折叠后，真实缺口是 **69 个内容文件**。
4. `restore-vault` 与 `fetchlocal` 两次重建尝试，各留下 2.3G / 1.3G，都没能取回那 69 个文件。

## 4. 两个真实缺陷

**打标（tagger）**：`https://qwen-coder-next.perilcrosser.com/v1` 连不上，每轮 `0 tagged, 18 failed (will retry next time)`。18 条会永远重试下去，日志每 2 小时刷一次 ERROR。GB10 是独立工作线，但 NAS 侧应该先止血：`tagger.enabled: false`，让这 18 条停在 pending 而不是无限重试。

**无视频的 pin**：`_is_supported_item`（`sync_engine.py:104`）只在 pin 带可用视频时返回 True，否则 `logger.debug` 一行就跳过，不通知、不归档、不移出收藏箱。结果是这类条目永远躺在收件箱里，`status` 也看不出来。要么支持纯文字/图片 pin，要么至少升成 WARNING 并走 notify。
