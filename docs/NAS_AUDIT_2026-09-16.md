# NAS Zhihu Pipeline 审计报告

审计日期：2026-09-16（Asia/Shanghai）  
范围：Mac 本地项目、QNAP NAS `192.168.1.195`、Container Station 中的 `zhihu-pipeline`

## 初次审计结论摘要

- NAS 本身可达，SSH 登录正常；问题不是网络不可达或权限不足。
- QNAP 的 Docker 客户端不在普通 SSH 的 `PATH` 中，实际引擎通过 Container Station 专用客户端和 `/var/run/docker.sock` 工作。
- `zhihu-pipeline` 是 Compose 项目；初次审计时实际状态为 `Exited (137)`。Docker 事件显示先收到 `SIGTERM`，约 10 秒后收到 `SIGKILL`；`OOMKilled=false`，与手工强制停止相符。
- 容器停止前持续收到 Telegram `getUpdates` 的 HTTP 404。用 NAS 当前配置中的 token 调用 `getMe` 仍返回 404，因此 Telegram 配置当前不可用。
- 初次审计时 NAS 和 Mac 访问 GB10 Qwen 地址均返回 Cloudflare `530 / error 1033`，所以当时打标签服务不能作为可用依赖验收。
- 初次审计时 NAS 上运行的源码没有包含本次 Mac 侧的安全修复：manifest 损坏时仍会被当成空 manifest，Git push 仍然执行全库 `git add -A`，Git pull 失败后仍会继续同步。
